# Central Admin HTTPS + TURN — deployment and proof runbook

**Status: NOT DEPLOYED by this repository.** GitHub Pages cannot execute Node services, store secrets or relay WebRTC packets. Production deployment needs an operator-managed publicly reachable DNS name, VPS/container host, private volumes, TLS certificates, firewall ports and private credentials; none were supplied in this project chat. Commit code/doc updates only; do not claim a hosted service is live.

## 1. Admin HTTPS service (independent of static GitHub Pages)
1. Provision a dedicated HTTPS DNS name such as `admin.yourdomain.example`; point it to your managed VPS, enable TLS 1.2+, auto-renewed certificates, firewall and backups. Restrict the Node server to `127.0.0.1:4173` behind a trusted TLS terminating reverse proxy. If containers are used, bind the app only on the private bridge network.
2. Privately configure `ZEBJUS_PUBLIC_ORIGIN=https://admin.yourdomain.example`, `ZEBJUS_DEVELOPER_PASSWORD=<unique privately provisioned long password>`, `ZEBJUS_ADMIN_DATA_DIR=<private persistent volume outside webroot>`, `HOST=127.0.0.1`, `PORT=4173`. Never put real secrets in Git, URL parameters, browser JavaScript or CI logs. Restrict filesystem mode to the service account; back up encrypted.
3. Run `node server.cjs` with Node.js 22+ as an unprivileged user. Configure reverse proxy to forward the original Host/Origin, disable caching of `/api/admin/*`, allow only HTTPS, apply rate/size limits, security headers and intrusion monitoring. Host the WebApp on **this same HTTPS origin** if you need its relative `/api/admin` UI; opening the GitHub Pages copy alone cannot call this API.
4. Probe `https://admin.yourdomain.example/api/admin/session` and require `{"available":true,"user":null}` without a cookie, then log in through the real UI from two locations. Test wrong password/lockout, staff create/revoke, logout, session expiry, CSRF/origin rejection, reboot persistence and backups. Never share login secrets in result logs.

## 2. TURN relay and ephemeral credentials
1. Deploy **coturn** with a real relay IP and DNS, STUN/TURN UDP 3478, TURN TLS TCP 5349, restricted UDP relay port range and host firewall allowances; create a real TLS certificate and disable anonymous access. Protect administrative ports.
2. Use authenticated REST-style time-limited credential generation in an independent HTTPS service. Store the coturn shared secret **only** in its private environment/secret manager. Validate session authentication, origin authorization, rate limits, short expiry (ideally 60–120 seconds, maximum 10 minutes), safe CORS to the actual WebApp origin and no access without a logged-in identity. Never expose permanent credentials through static `remote-rtc-config.json`.
3. Credential endpoint must return `{expiresAt:<Unix ms>,iceServers:[{urls:["turns:relay.example.org:5349?transport=tcp","turn:relay.example.org:3478?transport=udp"],username:"<ephemeral>",credential:"<ephemeral>"}]}`. Configure the **URL only** in `remote-rtc-config.json` after real deployment; do not commit actual usernames or secrets.
4. Test unauthenticated credential request -> 401 or 403; authenticated -> temporary non-cacheable response; expired/replayed cookie/credentials -> denied, invalid timestamp -> denied. Verify all secret fields are redacted from logs.
5. **Proof of real relay:** Run WebRTC `getStats` on Android cellular and school wired/Wi-Fi behind a restrictive NAT, record selected ICE candidate **type relay**, datachannel round-trip/timeout and disconnect handling. Confirm Android grants only read-only Kit telemetry and simulator control; no remote physical motor/control/OTA/wifi write endpoint is forwarded.
6. Run `ZEBJUS_PUBLIC_ORIGIN=https://... ZEBJUS_TURN_CREDENTIALS_URL=https://... npm run verify:remote-deployment` as a basic *reachability/auth-boundary* preflight (not relay test), then record the independently observed results as `ADMIN_HTTPS_DEPLOYED` and `TURN_RELAY_DEPLOYED` in the acceptance evidence file.

## Production announcement gate
Do not state "remote works over any network" merely because STUN is configured, `TURN ready` is displayed, a credential fetch succeeded, or localhost tests pass. Confirm TLS, authenticated credentials, relay candidates, school firewall, real carrier connectivity and operator evidence first. Do not promise TURN uptime without infrastructure monitoring/alerts and outage procedure. Until then, the accurate product description is **STUN-only / TURN not verified; remote Kit telemetry is read-only, virtual simulator control only**.
