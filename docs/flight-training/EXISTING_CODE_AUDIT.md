# Implementation audit

Baseline: `80bd3376c2b2201e77d9480b8affde149f3b2165`, Web `1.6.0+23`, Android code 11. The existing repository was inspected before modification. Its 83 baseline unit tests passed. The reference repository and supplied wireframes/guides were used for interaction and visual comparison; the Aerion APK was not installed, executed, copied into runtime assets or used for signing.

| Baseline finding / cause | Implemented change | Relevant evidence |
|---|---|---|
| Android `setupStick()` refused pointer-down unless connected, owned and armed. Unpaired/unarmed sticks therefore appeared frozen. | Rendering/capture accepts touches independently of flight authorization; disconnected preview never integrates throttle or sends flight commands. Initial displacement is exactly zero. Each zone holds its own pointer ID; cancel/release cannot steal the other pointer. | CDP touchscreen at six sizes including native density; production WebView MotionEvent acceptance; `flight-input.test.mjs` |
| Independent Tripod document plus Android Flight iframe duplicated simulator destinations and used asynchronous `postMessage` receiver readiness. | Canonical `/tripod.html`; one direct `ZebjusTraining` receiver, one plant and RAF. Legacy hashes redirect; iframe/postMessage receiver and timers removed. | DOM contracts, audit browser and actual paired WebRTC |
| Local frame updates and local knob rendering could overwrite remote axes. | Exclusive authenticated owner determines which source drives physics; mirrored Android raw sticks are display-only, accepted axes drive the plant. Web PID/environment controls remain usable. | Paired dual-stick, keyboard exclusion and live PID tests |
| Screenshot review found the Web header retained a pairing-time MOTORS OFF message during receiver-applied ARM. | Header ARM/DISARM transitions now follow the actual plant state for both sources while preserving live tuning messages. | Actual paired WebRTC asserts the active and stopped banner against applied state |
| Pairing only lived in the main Settings/LED flow. | Full existing QR/code/PIN workflow moved into the Flight header gear. Dialog header STOP stays available in every step. Closing settings stops the camera and preserves the valid RTC session. | QR pixel decode, real channel, camera cancel/reopen and settings tests |
| Virtual LED transport/UI was obsolete but shared approval/ownership code. | Removed LED packets, API methods, buttons, styles and demo tabs end-to-end. Preserved approval, session validation, ownership and physical wiring/Python LED examples. | Source/DOM contract and legacy lab regressions |
| No quantitative constrained vertical DOF; visuals had limited lift cue. | Explicit SI motor force and spring/damper slider, weight/support/travel/velocity/force UI and attached moving mast. | RPM lag/quadratic force tests, CSV, rendered mast assertions |
| Physics/mixer signs and finite tuning needed proof. | Exact exponential actual RPM, consistent cross-product motor torque and reactive yaw, bounded body constraints, cascaded PID, bumpless gain application, antiwindup and reproducible seeded noise. | 25 physics tests, equal-condition seven-preset traces |
| Audio was loud/harsh and visual movement did not disclose numerical travel. | Quiet 25% default, sine layers, low-pass wash, smoothing/limiter, persistent mute/volume/profile, explicit 2× visual travel and measured actual motor effects. | Instrumented voice/STOP/disposal/persistence and visual tests; subjective acoustics remain unverified |
| Delayed feedback could restore an older mode or treat pre-ARM telemetry as a fresh DISARM. | Mode changes supersede outstanding old-mode ACKs; ACK sequence/session checks and owned telemetry watermark reject stale feedback. | Actual 80/220/300 ms reordered feedback with ACK loss over encrypted RTC |
| Release identity must survive an update. | Same package and pinned production certificate; code 12/name 1.6.1-flight-training. Secret-backed signing, debug exclusion and old-release in-place native upgrade are required gates. | Real apksigner/aapt and available API-35 native acceptance |

Retained source/assets: Assembly transforms and GLBs, Wiring, Python editor/worker/Monaco/Pyodide/Matplotlib, USB I²C examples, Firmware Center and unchanged scanner image hashes. No ESP32/AP/STA/UDP/real-motor feature was introduced. Existing Android secure asset origin, exact camera-video permission, denied-permission handling, inset application and network/lifecycle wrapper remain in place.

Implementation files are `companion*.js/html/css`, `flight-input.js`, `pairing-core.js`, `pairing-web.js`, `tripod.html/css`, `js/training-receiver.js`, `js/tripod-physics.js`, `js/tripod-page.js`, `js/tripod-experiments.js`, `js/tripod-audio.js`, navigation/cache/version metadata and test/release workflows. New test-only instrumentation injects Android touchscreen events into the production WebView; no production debug bridge is enabled.

Two test infrastructure defects were exposed before release: the Web version contract requires `+build`, so the candidate marker was corrected to `1.6.1+0`; the emulator runner lacked `rg`, so its acceptance script uses POSIX grep. The old-release preference fixture is closed gracefully before force-stop so Chromium can flush asynchronous DOM storage. These failures were recorded and were never counted as native touch success.

Native API35 also exposed an actual compact-screen/STOP defect: a1280×720 display at emulator density produced a488×227 CSS viewport, so the old single-row header clipped STOP. The header now uses two rows below600px and preserves44px actions; real native third-finger STOP uses pointer-down because a non-primary touch need not synthesize click. The final native runner uses system `UiAutomation.injectInputEvent` and asserts the actual WebView response, with four normal/reverse cases and no JS touch surrogate. Reference: https://developer.android.com/reference/android/app/UiAutomation#injectInputEvent(android.view.InputEvent,%20boolean).
